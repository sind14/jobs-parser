# LinkedIn Jobs Parser (Python + Django + PostgreSQL)

Парсер вакансій LinkedIn за пошуковим запитом і країною. Складається з двох незалежних частин:

| Частина | Команда | Що робить |
|---|---|---|
| **1. Search** | `python manage.py run_search` | Шукає вакансії з пагінацією, зберігає картки (id, назва, компанія, локація, дата…) і компанії в PostgreSQL |
| **2. Details** | `python manage.py run_details` | Бере з БД необроблені вакансії та компанії, збирає повну інформацію і оновлює записи |

Плюс Django-адмінка (пошукові запити, вакансії, компанії) і вивантаження в CSV / Excel.

---

## Запуск однією командою (з уже зібраними даними)

Потрібен лише [Docker](https://www.docker.com/products/docker-desktop/).

```bash
git clone <посилання на цей репозиторій>
cd <назва папки>
docker compose up
```

Перший запуск триває 1–3 хвилини: збирається образ, і PostgreSQL завантажує знімок зібраних
даних (`docker/initdb/01-demo-data.sql.gz`). Після цього відкрийте
**http://localhost:8000/admin/** — логін `admin`, пароль `admin` (демо-доступ лише для
локального запуску). Одразу доступні всі зібрані вакансії й компанії.

Парсер можна запустити зі свого комп'ютера всередині контейнера:

```bash
docker compose exec web python manage.py check_access        # чи віддає LinkedIn дані вашій IP
docker compose exec web python manage.py add_query "Python Developer" "Poland" --max-jobs 100
docker compose exec web python manage.py run_search
docker compose exec web python manage.py run_details
```

Або з адмінки: дії «▶ Запустити Search / Details» у списку пошукових запитів.
Зупинити — `docker compose down`; почати з чистого знімка — `docker compose down -v`, потім знову
`docker compose up`.

## Локальна розробка

Вимоги: Python 3.12+ (цього вимагає Django 6), Docker (для PostgreSQL) або власний PostgreSQL 14+.

```bash
# 1. База даних (лише контейнер БД; при першому запуску теж підвантажить знімок даних)
docker compose up -d db         # PostgreSQL 17 на localhost:5433

# 2. Оточення
python -m venv .venv
.venv\Scripts\activate          # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env            # за потреби змініть доступи до БД

# 3. Міграції та користувач адмінки
python manage.py migrate
python manage.py createsuperuser

# 4. Адмінка
python manage.py runserver      # http://127.0.0.1:8000/admin/
```

### Запуск парсера

Пошуковий запит створюється в адмінці (**Пошукові запити → Додати**) або з консолі:

```bash
python manage.py add_query "Python Developer" "United States"
python manage.py add_query "Python Developer" "Germany"
```

```bash
# Частина 1 — Search: усі активні незавершені запити (або --query-id N)
python manage.py run_search

# Частина 2 — Details: вакансії + компанії (паралельно, 6 потоків за замовчуванням)
python manage.py run_details --workers 6

# Вивантаження
python manage.py export_jobs --format xlsx -o export/linkedin_jobs.xlsx
python manage.py export_jobs --format csv  -o export/linkedin_jobs.csv
```

Обидві частини можна запускати й з адмінки: дії «▶ Запустити Search» / «▶ Запустити Details»
для вибраних пошукових запитів (запускаються окремим фоновим процесом). Вивантаження CSV/Excel —
теж через дії у списках запитів і вакансій.

Корисні прапорці:

| Команда | Прапорець | Призначення |
|---|---|---|
| `run_search` | `--query-id N` (можна кілька) | лише вказані запити |
| | `--restart` | забути збережений прогрес і пройти пошук заново (дані не видаляються) |
| | `--include-done` | повторно пройти й уже завершені запити (підхопити нові вакансії) |
| `run_details` | `--workers N` | кількість потоків |
| | `--limit N` | обробити не більше N записів за запуск |
| | `--query-id N` | лише вакансії / компанії цього запиту |
| | `--jobs-only` / `--companies-only` | лише вакансії / лише компанії |
| | `--follow` | коли черга порожня — чекати на нові вакансії, поки працює Search |
| `export_jobs` | `--query-id N`, `--only-done` | фільтри вивантаження |
| `reparse` | `--kind job\|company`, `--key ID`, `--dry-run` | перепарсити збережений HTML без запитів до LinkedIn |
| `check_access` | `--only search\|job\|company` | безпечно перевірити, чи LinkedIn знову віддає дані цій IP (див. нижче) |

## Які API використовуються (знайдено через DevTools → Network)

На публічній сторінці `https://www.linkedin.com/jobs/search?keywords=…&location=…` (без логіну):

1. **Пошук** — запит під час прокрутки стрічки / кнопки *See more jobs*:
   `GET https://www.linkedin.com/jobs-guest/jobs/api/seeMoreJobPostings/search?keywords=Python%20Developer&location=United%20States&start=0`
   → HTML-фрагмент з 10 картками; `start` — зміщення (крок 10).
   Реально працюючі параметри: `location` / `geoId` і `f_TPR` (давність публікації).
2. **Вакансія** — запит при кліку на картку (права панель):
   `GET https://www.linkedin.com/jobs-guest/jobs/api/jobPosting/{job_id}`
   → опис, seniority, employment type, industries, кількість відгуків, зарплата,
   тип відгуку (Easy Apply / на сайті компанії), ознака закритої вакансії.
3. **Компанія** — публічна сторінка `GET https://www.linkedin.com/company/{slug}`:
   JSON-LD `Organization` (назва, опис, сайт, кількість співробітників на LinkedIn, адреса, логотип)
   + блок *About us* (галузь, розмір, головний офіс, тип, рік заснування, спеціалізації)
   + кількість підписників.

Відповіді — серверний HTML, розбирається BeautifulSoup + lxml (`jobs/linkedin/parsers.py`).

### Обхід ліміту пагінації (збір «усіх доступних» вакансій)
Гостьовий пошук віддає не більше ~1000 результатів на один пошук (`start` ≥ 1000 → HTTP 400).
Тому запит обробляється як дерево **зрізів** (`SearchSlice`):

1. Спочатку проходиться базовий зріз (ключові слова + країна).
2. Якщо зріз «вперся» в ліміт (≥ `LI_SLICE_SPLIT_THRESHOLD` = 900 карток), він автоматично
   ділиться **за регіонами країни** (`location=California, United States`, …). Регіони — це
   розбиття країни без перетинів, і кожен регіон зазвичай менший за ліміт.
   Вбудовані списки є для США, Канади, UK, Німеччини, Польщі, України, Індії, Австралії;
   для інших країн регіони можна задати в адмінці (поле «Регіони для розбиття»).
3. Якщо й регіон упирається в ліміт — він ділиться за давністю публікації
   `f_TPR` = 24 години / тиждень / місяць (вікна перетинаються, але піднімають свіжі вакансії,
   що не влізли в ліміт).

> Важливе спостереження під час дослідження API: гостьовий endpoint **мовчки ігнорує** фасети
> `f_E` (досвід), `f_JT` (тип зайнятості), `f_WT` (remote/hybrid) — видача з ними ідентична
> видачі без них. Працюють лише `location`/`geoId` і `f_TPR`, тому розбиття побудоване на них.

Перетини зрізів не страшні — дублі відсікаються на рівні БД.

### Виключення дублів
* `Job.job_id` — `UNIQUE`, вставка через `bulk_create(ignore_conflicts=True)`.
* `Company.slug` — `UNIQUE` (slug з URL компанії).
* Зв'язок вакансія ↔ пошуковий запит — M2M: вакансія, знайдена кількома запитами,
  зберігається один раз, але прив'язана до всіх.
* `SearchQuery` унікальний за (keywords, location, time_posted); `SearchSlice` — за (query, filters).

### Обробка помилок і повторний запуск
* HTTP: таймаути, до `LI_MAX_RETRIES` повторів, експоненційний backoff на 429 / 999 / 5xx /
  перенаправлення на authwall.
* **Сторінка-перевірка «ви бот?» з кодом 200.** Під час дослідження API LinkedIn одного разу
  віддав замість вакансії сторінку з обфускованим JS і автоперенаправленням — зі статусом 200.
  Без окремої перевірки Details сприйняв би її як «невідому розмітку», а Search — як кінець
  видачі, і зріз мовчки обрізався б. Тепер така відповідь розпізнається (`is_bot_check_page`)
  і обробляється як блок: пауза, зниження швидкості, повтор, запобіжник.
* **Адаптивний rate limiter (AIMD)** — спільний для всіх потоків процесу: на кожен 429/999
  швидкість зменшується вдвічі і *всі* потоки роблять спільну паузу, після кожної успішної
  відповіді швидкість плавно зростає. Так парсер сам знаходить стелю, яку LinkedIn допускає
  з однієї IP (на практиці ~1–2 запити/с), замість того щоб засипати сервер запитами.
* **Окремий обмежувач для сторінок компаній.** LinkedIn захищає їх значно жорсткіше, ніж
  вакансії, тому в компаній свій, повільніший темп (старт 0.15, мінімум 0.03 запиту/с), а після
  блоку сесія з cookies зберігається, як у звичайному браузері.
* **Запобіжник (circuit breaker).** Якщо LinkedIn блокує `LI_MAX_CONSECUTIVE_BLOCKS` (15) запитів
  поспіль навіть на мінімальній швидкості — IP тимчасово забанено, і подальші запити марні.
  Тоді етап зупиняється сам: необроблені записи лишаються в черзі без витрачених спроб
  (не позначаються як помилкові), а повторний запуск пізніше продовжує з того самого місця.
  Search у такому разі зберігає курсор зрізу і пише причину зупинки в адмінці.
* **Search** зберігає курсор пагінації кожного зрізу в БД після кожної сторінки. Перерваний
  (Ctrl+C, падіння, блокування) запуск продовжується рівно з того самого місця. Зріз з помилкою
  повторюється до 3 разів, далі — статус `failed`; наступний запуск дає йому нові спроби.
* **Що робить повторний `run_search`:**
  * незавершений запит (є зрізи в черзі / перервані / з помилкою) — **продовжує з курсорів**;
  * запит, що зупинився на ліміті вакансій, має статус «Досягнуто ліміт» і пропускається,
    доки ліміт не піднято; після цього продовжує з місця зупинки, а не з нуля;
  * повністю завершений запит проходиться заново лише явно (`--query-id N` / `--include-done`);
  * запит, який уже виконується в іншому процесі, вдруге не запускається (інакше два процеси
    качали б ті самі сторінки); «мертвий» запуск (процес упав, прогресу немає 30 хв)
    розпізнається і може бути продовжений. Так само `run_details --follow` не чекає вічно
    на Search, який упав.
* **Details** — у кожної вакансії / компанії є статус `new → processing → done | failed | not_found`
  і лічильник спроб. `failed` автоматично повторюються (до `LI_DETAILS_MAX_ATTEMPTS`),
  `not_found` (404/410 — вакансію видалено) не повторюються. Записи, що «зависли» в `processing`
  (впав процес), звільняються через 30 хвилин.
* З адмінки можна повернути будь-які записи в чергу (дія «Поставити в чергу на повторний збір»).

### Як безпечно перевірити, чи LinkedIn зняв блок
Після бану не варто одразу запускати парсер: він за хвилину надішле десятки запитів і може
продовжити блок. Для перевірки є окрема команда:

```bash
python manage.py check_access                 # 3 запити: пошук, вакансія, компанія
python manage.py check_access --only company  # 1 запит — лише сторінка компанії
```

Вона робить **рівно один запит на кожен тип сторінки**, без повторів, з паузою між ними, і
нічого не записує в базу. Для кожного типу пише вердикт: `OK` (прийшли реальні дані),
`BLOCKED` (999 / 429 / сторінка входу / сторінка-перевірка на бота) або `UNCLEAR`
(відповідь 200, але без даних). Перевіряйте не частіше ніж раз на кілька годин: кожна
перевірка — це теж запити. Коли все `OK`, продовжуйте: `python manage.py run_details --companies-only`.

### Збереження сирого HTML і офлайн-перепарсинг
Details зберігає стиснутий (zlib) HTML кожної сторінки вакансії та компанії в окрему таблицю
`RawPage` — **до** парсингу, тож сторінка лишається навіть якщо парсер впав. Якщо в парсері
знайдено помилку або LinkedIn змінив розмітку, дані виправляються командою

```bash
python manage.py reparse            # усі збережені сторінки
python manage.py reparse --dry-run  # лише показати заповненість полів, нічого не змінюючи
```

без жодного нового запиту до LinkedIn (ліміти якого — головне обмеження цього парсера).
Вимкнути: `LI_STORE_RAW_HTML=0`. Розмір у стиснутому вигляді (заміряно): сторінка вакансії
~31 → 7 КБ, сторінка компанії ~410 → 44 КБ. Для 10 000 вакансій і ~2 700 компаній це
≈ 70 МБ + 120 МБ.

> Цей механізм додано після першого великого прогону: тоді сирі відповіді не зберігались.
> Для вакансій, зібраних до цього, сирого HTML немає; він з'являється для всіх нових запитів.

### Пріоритет компаній
Сторінки компаній LinkedIn пропускає найповільніше (~0.2 запиту/с), тому компанії обробляються
не в порядку додавання, а **за кількістю вакансій — найбільші роботодавці першими**.
Розподіл дуже нерівномірний: топ-100 компаній покривають ~47 % вакансій, топ-300 — ~62 %,
а 1 608 компаній мають лише по одній вакансії. На практиці: до ввімкнення пріоритету
оброблені компанії покривали 21 % вакансій, а вже через ~10 хвилин після — 55 %
(при тій самій швидкості запитів).

### Незалежність частин
Частини взаємодіють лише через PostgreSQL. Details бере роботу через
`SELECT … FOR UPDATE SKIP LOCKED`, тому:
* Details можна запускати одночасно з Search (з `--follow` він підхоплює нові вакансії
  в міру появи);
* можна запустити кілька процесів Details паралельно (зокрема на різних машинах) —
  вони не візьмуть один і той самий запис.

## Результати тестового прогону (17.11.2026)

Запит **«Python Developer» — United States**, ліміт 10 000, одна IP, без проксі.

| Показник | Значення |
|---|---|
| Унікальних вакансій | **10 009** (дублів за `job_id` — 0) |
| Зрізи пошуку | базовий (997 карток, вперся в ліміт) → 51 штат → великі штати (AZ, CA, CO…) → вікна за давністю |
| Час Search | ~1 год |
| Details по вакансіях | 10 009 / 10 009 `done`, 0 помилок, ~3 год 20 хв (паралельно з Search) |
| Унікальних роботодавців | 2 760; базові поля (назва, URL) — для всіх, повні дані — для 654 найбільших, які покривають **63 %** вакансій |

Заповненість полів вакансій: опис, seniority, employment type, industries, applicants — 100 %;
зарплата — 13 % (вказують не всі роботодавці); Easy Apply — 1 149; прив'язка до роботодавця — **100 %**.

Спочатку прив'язка була 99 %: 105 вакансій опублікували університети, чиї сторінки на LinkedIn
мають адресу `/school/…` або `/showcase/…`, а не `/company/…`, і парсер їх не розпізнавав.
Після виправлення ці 105 вакансій поставлено в чергу (фільтр в адмінці «Компанія → Порожнє» +
дія «Поставити в чергу») і перезібрано лише через endpoint вакансій — 108 запитів, ~1,5 хв:
усі 105 прив'язано (88 — сторінки університетів, 17 — showcase), додалось 42 роботодавці.

Статус запиту — **«Досягнуто ліміт»**: по США LinkedIn має більше вакансій, ніж ліміт 10 000,
і 55 зрізів чекають у черзі. Щоб дозібрати решту, достатньо підняти ліміт і запустити Search —
він продовжить з місця зупинки.

Обмеження, виявлені на практиці:
* LinkedIn з однієї IP допускає ~1–2 запити/с до вакансій; сторінки компаній захищені жорсткіше
  (HTTP 999 вже при ~0.2–0.3 запиту/с), тому збір деталей компаній — найдовша частина.
  Після ~5 годин запитів з однієї IP LinkedIn почав блокувати сторінки компаній навіть на
  швидкості 1 запит / 33 с — тому збір компаній зупинено запобіжником, решту можна дозібрати
  пізніше командою `run_details --companies-only` (продовжить з місця зупинки).
* Гостьова картка вакансії не віддає `job function` і пряме посилання на відгук на сайті
  роботодавця. Перевірено на 14 сторінках, збережених під час дослідження API, і на 105
  сторінках, перезібраних пізніше зі збереженням сирого HTML (`reparse --dry-run`): у кожній
  лише 3 критерії (Seniority level, Employment type, Industries), «Job function» і зовнішнього
  посилання на відгук немає в жодній. Поля залишено в моделі — вони заповняться, якщо LinkedIn
  почне їх віддавати.
* Пошук за ключовими словами в LinkedIn «семантичний» — за запитом *Python Developer* приходять
  і суміжні вакансії (Data Engineer, Software Engineer тощо). Це поведінка самого LinkedIn.

Вивантаження: `export/linkedin_jobs.xlsx` (у репозиторії) і `export/linkedin_jobs.csv` (67 МБ —
генерується командою `export_jobs`, у git не зберігається) — один рядок на вакансію,
усі поля вакансії + усі поля компанії (`company_*`).

## Оновлення даних у репозиторії

Після нового запуску парсера (наприклад, коли дозібрано деталі компаній):

```bash
python scripts/update_demo_data.py
git add -A
git commit -m "Update collected data"
git push
```

Скрипт оновлює знімок бази `docker/initdb/01-demo-data.sql.gz` (без користувачів, сесій і
сирого HTML) і `export/linkedin_jobs.xlsx`. Хто вже запускав проєкт раніше, отримає нові дані
після `docker compose down -v` і `docker compose up` (знімок завантажується лише в порожню базу).
